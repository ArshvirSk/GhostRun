# GhostRun — Specification: Rematch & Role Rotation (NF-03)

> **Status:** Implemented (Wave 1 · NF-03)  
> **Companions:** `docs/WAVES.md`, `docs/NEW_FEATURES.md §4 (NF-03)`, `supabase/migrations/20261102002000_v2m2_start_and_rematch.sql`

---

## 1. Executive Summary

Playing consecutive rounds with identical role assignments causes runner fatigue and prevents players from experiencing both stealth evasion and hunter tracking.

**NF-03 (Rematch & Role Rotation)** guarantees that:
1. When rematching, player roles are **rotated systematically** so previous hunters deploy as runners, and active runners rotate into the hunter squad.
2. **Hunter Ratio Guard**:
   - At least 1 hunter per lobby.
   - Target hunter count: $\lfloor N / 3 \rfloor$.
   - Hard upper bound: $\lfloor (N - 1) / 2 \rfloor$ (hunters never outnumber runners).
3. The lobby host can invoke `"Rotate Roles"` or `"Randomize Teams"` at any time during the lobby phase.

---

## 2. Server Schema & RPCs

### 2.1 Database Migration
`supabase/migrations/20261118027000_nf03_rematch_rotation.sql`:
- RPC `rotate_teams(game_id uuid)`:
  - `SECURITY DEFINER`
  - Validates caller is host and game is in `lobby`.
  - Determines previous roles from `games.mode_params->'rematch'->'previous_roles'` or current team assignments.
  - Inverts previous hunters into runners.
  - Promotes next batch of runners to hunters to meet the ratio guard.
- RPC `rematch_game(p_game_id uuid, p_rotate boolean DEFAULT true)`:
  - Clones game and copies active players.
  - When `p_rotate` is true, automatically invokes rotation logic so the new lobby starts with fresh role distribution.

## 3. Client UI & Flow

1. **`app/result/[id].tsx`**:
   - Primary action: `"Play Again (Rotate Roles)"` calling `rematch_game(gameId, true)`.
   - Secondary action: `"Play Again (Keep Roles)"` calling `rematch_game(gameId, false)`.
2. **`app/lobby/[id].tsx`**:
   - Host controls include both `"Rotate Roles"` and `"Randomize Teams"`.
